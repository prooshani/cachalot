## 1. Headline result

The working configuration changed from "FP4 experts, 28 GiB budget, everything default" to "calibrated 3-bit
experts on the internal SSD, 44 GiB budget, page cache enabled", and the interactive experience changed with it.
Both rows are the same three-turn conversation typed into `cachalot chat` on this machine.

| | session start | session end |
|---|---|---|
| time to first token, turn 1 | 2.9 s | 1.1 s |
| time to first token, turn 2 | 10.5 s | 0.6 s |
| time to first token, turn 3 | 10.8 s | 1.1 s |
| decode, turns 1 / 2 / 3 | 3.73 / 3.06 / 3.54 tok/s | 4.34 / 4.77 / 5.57 tok/s |
| expert hit rate | 73.3 % | 79.3 % |
| resident experts | 1,599 | 3,032 |
| turn 2 wall clock, short answer | 14.1 s | 2.5 s |

Decode improved about 40 % as a geometric mean across turns. Follow-up time to first token improved by roughly
an order of magnitude. Output quality is unchanged within measurement: teacher-forced negative log-likelihood
moved from 2.3004 to 2.3080 nats, perplexity 9.978 to 10.054, top-1 accuracy 53.1 % on both.

Five independent changes produced this, and each was measured separately. They are, in order of contribution:
the 3-bit expert bank, the larger budget it permits, the idle heartbeat, typing-time prefill, and the OS page
cache acting as a second-level cache.

### 2.2 Checkpoint composition, measured from the shard headers

The shipped FP4 checkpoint is 48 shards totalling 475.2 GiB:

- **trunk**, 10.4 GiB, smeared across 46 shards that also hold experts
- **routed experts**, 275.7 GiB across 43 shards
- **Engram**, 189.1 GiB in exactly two pure shards, numbers 47 and 48, 94.56 GiB each

Engram is therefore trivially separable and the trunk is not. Engram layers are 1 and 14; each holds
`embed.weight` as F8_E4M3 of shape [384006168, 256] plus `embed.scale` as F8_E8M0 of shape [384006168, 8].

The 3-bit conversion (`Jundot/DeepSeek-V4.1-Flash-oQ3e-mtp`, 65 shards, 331 GB) contains 228.2 GiB of experts,
91.9 GiB of Engram, 10.1 GiB of trunk and 0.8 GiB of unused draft weights.

## 4. Measured curves

### 4.1 Budget sweep, 3-bit bank on internal SSD

`benchmarks/decode_throughput.py --prompt-tokens 512 --decode-tokens 64`, page cache on, mirror off.

| budget | decode | hit rate | misses per token | peak wired |
|---|---|---|---|---|
| 28 GiB | 3.22-3.36 tok/s | 69.5 % | 73.3 | 52.6 GiB |
| 32 GiB | 3.47 tok/s | 72.3 % | 66.5 | 56.8 GiB |
| 36 GiB | 3.64 tok/s | 74.7 % | 60.8 | 60.0 GiB |
| 40 GiB | 3.78 tok/s | 76.4 % | 56.6 | 63.2 GiB |
| 44 GiB | 3.89 tok/s | 77.8 % | 53.3 | 67.4 GiB |

Prefill of 512 tokens is flat at 24.2 s at every budget. Returns are still positive but flattening, roughly
+0.11 to +0.17 tok/s per additional 4 GiB. Run-to-run noise is about 4 %. Going beyond 44 GiB needs more than
73 GiB of available memory, which the guardian will refuse while applications are open.

The FP4 baseline for comparison, all on the internal SSD at 28 GiB with the page cache on, was 2.89 tok/s at
65.6 % hit rate with 82.5 misses per token and a 28.8 s prefill.

### 4.4 Quality gate

`benchmarks/nll_expert_precision.py`, 160 tokens teacher-forced after a 48-token prefill:

| arm | mean NLL | perplexity | top-1 | vs FP4 |
|---|---|---|---|---|
| FP4, dense reference math | 2.3004 | 9.978 | 53.1 % | — |
| 3-bit, dense reference math | 2.3398 | 10.379 | 52.5 % | +0.0394 nats |
| 3-bit, production runtime | 2.3080 | 10.054 | 53.1 % | +0.0076 nats |

The production path scores better than its own dense reference because `mx.quantized_matmul` accumulates more
carefully than dequantizing and rounding through bfloat16; the reference arm is the pessimistic one. Greedy
agreement with FP4 is 141 of 160 tokens, which is normal: this model's greedy decoding flips on far smaller
numeric changes than a quantization step.

Weight-space error is large and harmless: relative RMS 0.174 on the gate and up projections, 0.18 on the down
projection, and 0.29 to 0.31 relative error on the expert output, uniform across all 40 layers. Uniformity is
the signature of honest quantization noise rather than a layout bug.

## 5. Operating rules

These exist because this machine kernel-panicked twice on 2026-09-15, at 17:51 and 18:00. The panic report is
`/Library/Logs/DiagnosticReports/panic-full-2026-09-15-180051.0002.panic`: a watchdog timeout with the
compressor at "100 % of segments limit", 29 swapfiles and low swap space. The cause was benchmarks running with
the automatic expert budget, which wires about 67 GiB on this machine; with other applications open that
overflowed into swap, the boot volume had 13 GiB free, and `kernel_task` spun compressing until the hardware
watchdog rebooted.

1. **Never run the runtime with an automatic expert budget.** Always pass `--expert-budget-gib` or set
   `CACHALOT_EXPERT_CACHE_BUDGET_GIB`. The automatic formula still chooses 47-50 GiB on this machine.
2. **Every benchmark goes through `benchmarks/guarded_run.sh`.** It refuses to start when another runtime is
   alive, when memory pressure is not normal, when the boot volume is nearly full, or when free plus reclaimable
   memory cannot hold the planned wired set. While running it samples `vm_stat`, swap, pressure, RSS, the
   compressor and the largest other process every second into
   `benchmarks/results/guarded/<tag>_<timestamp>.csv`, and it kills the command on critical pressure, on
   sustained warning pressure, on swap growth, on low disk, on timeout, or when the runtime reports a larger
   budget than was requested. It has already saved this machine once, killing a run at 2.6 GB of swap.
3. **One runtime process at a time.** Benchmark arms run sequentially, never in parallel.
4. **Interactive chat is not guarded.** It relies on the explicit budget instead, which is why section 3 gives
   two settings rather than one.

### 5.1 Working style expected in this project

- Every repository edit goes through shell commands, never prose asking for a manual edit.
- Every command given to the user is complete and copy-paste ready: absolute `cd`, `PYTHONPATH=src`, the full
  interpreter path. Never a bare `python`, never an ellipsis.
- Measure before changing behaviour. One architectural change at a time. A/B every optimization.
- After each production patch: byte-compile, run the focused test, `git diff --check`, inspect the diff.
- Benchmark scripts stay out of runtime code.
- Model output quality must be preserved; performance work must not silently change semantics.
- Chat replies terse; prose in files, commits and documents normal and complete.

## 6. What changed today, and why

Seven commits, oldest first.

**`2707a21` One-layer-early routing prediction.** Layer L+1's router is applied to the activation layer L's
router sees, and the top-k predicted experts begin loading into free transient slots while the GPU runs layer L.
A predicted expert becomes resident only when a layer actually asks for it; unclaimed loads return their slot at
the next sweep. Decode went from 2.26-2.34 to 2.55 tok/s at a 28 GiB budget. `CACHALOT_PREDICT_TOPK` defaults to
3: top-2 gave 2.43 with 86 % precision, top-4 gave 2.44-2.47 with 72 % precision and 14.6 wasted loads per
token. Because the SSD is bandwidth-bound, wasted prefetch bytes cost exactly what early hits save.

**`f965ca4` Environment overrides applied when a value is automatic.** `TextDecodeRuntime` replaced the
environment-loaded config unconditionally, so its default of 0 discarded `CACHALOT_EXPERT_CACHE_BUDGET_GIB` and
`CACHALOT_MLX_WIRED_LIMIT_GIB`. This is the bug behind the panics: benchmarks that asked for 32 GiB ran at the
47-50 GiB automatic budget. An explicit constructor value still wins; 0 now defers to the environment and only
then to the formula.

**`83015d4` Idle heartbeat.** Within about six seconds of an idle Metal queue, macOS un-wires the entire working
set despite `mx.set_wired_limit`. The guardian trace shows wired memory falling from 49.8 to 6.6 GiB, anonymous
memory rising to 40.7 GiB, and the compressor reaching 43.6 GiB. The next forward pass then pays the
decompression, which is why a 13-token follow-up prefill took 10.5 s after a typing pause but 2.9 s when the
same turns were replayed back to back. A daemon thread now evaluates a one-element MLX operation every
`idle_heartbeat_seconds`, default 0.5, while no forward pass runs. Replayed with 45-second gaps, wired memory
stays flat at 49.5 GiB.

**`e299e22` Typing-time prefill, and short prefills keep the cache.** On an interactive terminal the chat reads
keystrokes raw and, after 0.4 s without a key, prefills the template head plus the finished words of the message
through the prefix cache. Enter then pays only for the last word and the template tail. A pseudo-terminal typing
at human pace reused 50 of 57 prompt tokens instead of 37 and waited 2.0 s instead of 5.5 s. The same commit
fixes prefill admission, which used to evict every resident of a layer the prompt did not route to; the 2-3
token speculative prefills shrank the resident set from 1,599 to 453 experts and cost four points of hit rate.

**`56f87c7` and `bf092b5` The memory guardian.** Described in section 5.

**`2edea1a` Expert bank abstraction.** `CACHALOT_EXPERT_BANK` serves routed experts from a different directory
than the trunk, Engram and tokenizer. `storage.index.detect_expert_bank` recognises an oMLX-converted checkpoint
from `omlx_deepseek_v41` in its `config.json` and indexes the stacked per-layer tensors into per-expert byte
ranges. The slot pool and resident store accept any tensor set. `model/expert_affine.py` evaluates the official
routed-expert arithmetic on the slot views with `mx.quantized_matmul`. Decode and batched prefill branch on the
store's format. The reader reads an expert's pieces concurrently, which matters because nine scattered reads of
a 15.5 MiB expert take 4.2 ms serially and 2.8 ms in parallel at the same aggregate bandwidth.

**`3e89a0c` Release 0.3.0.**

## 7. Open levers, ranked

### 7.1 Move Engram onto the internal SSD

**Why it is first.** Every prefill reads Engram rows, and they currently come over USB at 1.0 GB/s. The shipped
Engram is 189.1 GiB and will not fit in the 147 GiB free. The 3-bit conversion carries the same two layers at
91.9 GiB, already sitting on the internal disk inside the bank directory. Reading those instead would put the
whole model on fast storage and retire the USB dependency entirely.

**What it needs.** The Engram reader currently assumes the shipped format, F8_E4M3 values with F8_E8M0 block
scales, and dequantizes rows on lookup. The 3-bit tables are MLX affine, 3-bit, group 32, stored as a U32 weight
of shape [384006168, 24] with bf16 scales and biases of shape [384006168, 8]. The row gather and the
dequantization both need a second path, in the same shape as `model/expert_affine.py`.

**Risk.** Engram is the model's n-gram memory and today's quality gate did not touch it. This needs its own
teacher-forced NLL run before it is adopted, with the experts held constant.

**Expected gain.** Prefill only; decode does not read Engram. Prefill is currently 24.2 s for 512 tokens against
a measured SSD floor, and earlier work established that Engram rows were once the hidden prefill cost.

### 7.2 Decayed-frequency eviction

Today's default is plain LRU. antirez's ds4, which solves the same problem, converged on decayed frequency:
each route adds one to an expert's hotness, all hotness values are halved every N decode tokens, and the victim
is the lowest hotness with oldest-used as the tiebreak. Our own replay predicted frequency-decay at 39 % against
LRU at 31 % on a 40 GiB budget, while a later note recorded only 1 to 2 points. That contradiction is unresolved
and worth one careful run, because at the current budgets a hit-rate point is worth more than any kernel work.
An opt-in sampled-LFU already exists behind `CACHALOT_EVICT`.

### 7.3 Mirror striping is currently harmful — leave it off

With the 3-bit bank, 28 GiB and the mirror on, decode fell from 3.22 to 2.74 tok/s. The cause is a code
interaction, not bandwidth: `ExpertReader._read_pieces_concurrently` is skipped whenever a mirror is configured,
so the bank's nine pieces per expert fall back to serial reads, and USB tail latency lands on top. It could be
fixed by teaching the mirror path to issue pieces concurrently, but there is little point while the bank lives
on the fast drive.

### 7.4 Startup hotlist preload

ds4 ships a static list of hot layer-expert pairs per model and fills the cache before the first token; Cachalot
starts cold. The routing trace needed to build one already exists in `benchmarks/trace_routing.py` and
`benchmarks/analyze_trace.py`. This mainly helps the first prompt of a session.

### 7.5 Smaller, more aggressive expert bank

ds4 ships a Q2-class imatrix-calibrated V4.1 bank at 152 GiB, against the 221.5 GiB of the 3-bit bank now in use
and the 275.7 GiB of FP4. Both levers that made today's gain would move again. It is GGUF and uses llama.cpp
k-quants, which MLX cannot read, so adopting it means either a GGUF reader plus k-quant Metal kernels or finding
an equivalent MLX-format conversion. Their mixed-precision recipe, mostly Q2 with the last six routed-expert
layers raised to Q4, is the quality trick to copy if this is attempted.

### 7.6 Smaller items

- `F_RDAHEAD 0` alongside `F_NOCACHE`, which ds4 sets and we do not. Cheap to test.
- Long-prompt prefill, 2048 tokens, has not been re-measured with the 3-bit bank.
- Budgets above 44 GiB, which need the machine close to idle.

## 8. Null results — do not repeat these

Each of these was measured and rejected. Re-running them costs hours and returns nothing.

**From today:**

- **LRU prefill admission** as an alternative to the quota planner. Decode misses per token were identical and
  prefill misses were higher on every turn of a six-turn replay. The code was removed.
- **Mirror striping with a stacked bank.** See 7.3.
- **Speculative decoding, MTP and DSpark.** Rapid-MLX's headline "2x" for V4.1 Flash is this, on a 256 GB M3
  Ultra with a fully resident pruned 2-bit checkpoint. Verification of K positions multiplies bytes per token,
  which is precisely the resource we are short of. Their all-resident autoregressive decode is 100-137 ms per
  token; ours is 68 ms. There is nothing to import.
- **Expert pruning or pinning a hot subset.** oMLX measured that zeroing the experts outside a usage-calibrated
  pinned half costs about 91 % of gsm8k accuracy. Fetch-on-miss keeps the computation exact.

**From earlier sessions:**

- Chunked expert reads; a single expert read already achieves 5.5 GB/s.
- A GPU heartbeat to prevent clock drop; the clock does not drop during decode.
- A fused multi-expert kernel and `gather_qmm` chunking; both slower than per-expert affine-8 quantized matmul.
- A simdgroup FP4 GEMM: 2.5× less GPU time, zero wall-clock change.
- The miss-budget approximation: 9.7 tok/s at budget 0, but KL 0.64 and only 7 of 40 identical tokens.
- Cache policy changes in isolation were worth 1 to 2 points, against 13 % fewer bytes from a larger budget.

## 9. Pitfalls worth knowing before touching the code

- **MLX streams are thread-local.** Evaluating a runtime graph from a worker thread raises
  `There is no Stream(gpu, N) in current thread`. Typing-time prefill runs on the chat thread for this reason.
  The heartbeat and forward passes share `runtime._gpu_lock`.
- **`tty.setcbreak` flushes pending input** unless called with `TCSANOW`. Without it, anything typed while the
  model was still generating is silently discarded.
- **Free memory is always near zero on macOS** because the file cache fills it. Judge pressure by
  `kern.memorystatus_vm_pressure_level` and by compressor growth, not by free pages.
- **Greedy decoding is near-tie sensitive.** Kernel changes at the level of a floating-point unit flip tokens
  within five steps. Judge numerics by teacher-forced NLL, never by comparing greedy text.
- **The occasional stutter in generated text** — "con concurrency", "nib nibbled" — appears with every numerics
  path including the fully unfused baseline. It is model behaviour, not a bug in this runtime.
- **A pseudo-terminal harness must drain the child's output while typing**, or the chat blocks writing to a full
  buffer and the test appears to hang.
