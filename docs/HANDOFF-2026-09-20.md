# Run A, the diagnostic — hosted reference vs Cachalot

Run 2026-09-20 with `benchmarks/run_reference.py`: bare API calls, no system
prompt, no tools, no content retries, reasoning disabled, provider pinned with
`allow_fallbacks: false`. Settings from `settings.json`: temperature 0.6,
top_p 1.0, max_tokens 2000, frequency_penalty 0.2, seeds 20260919 / 20260920.

Two reference arms were run rather than one, so that the FP4 expert format and
the serving stack could be separated:

- **`relace/fp4`** — FP4 quantization, the same `expert_dtype: fp4` the official
  checkpoint declares. This is the arm paired with Cachalot.
- **`deepinfra/fp8`** — FP8, as a contrast.

All four arms are 40 of 40 cases. Both reference arms finished `stop` on every
case and were served by exactly one provider: `{'Relace': 40}` and

they are two real samples per task even though Relace does not advertise `seed`.

## Greedy, the same six cases at temperature 0

| | Cachalot greedy | run A fp4 greedy |
|---|---|---|
| C++ blocks that compile | 0 / 6 | **6 / 6** |
| aborted on a fatal include | 4 / 6 | 0 / 6 |
| `#include` lines malformed | 1980 / 2004 (99 %) | **0 / 34 (0 %)** |

Cachalot's greedy replies emit thousands of malformed include lines because the
model keeps self-correcting and reproduces the same corruption every time. The
reference, greedy, on the same six prompts, emits none.

## What this settles

On the RUN.md decision table this is unambiguously **"reference clean, Cachalot
corrupt"**: the fault is in the runtime, the kernels or the serving path.

Three alternative explanations are now closed:

- **Not FP4.** The `relace/fp4` arm serves FP4 and is clean at 0 %.
- **Not the harness.** Run A has no harness at all and is clean, so run B's
  clean result was not the harness rescuing anything.
- **Not sampling.** Greedy decoding on both sides keeps the gap at 0 % versus
  99 %.

The remaining suspect is Cachalot's own path: expert streaming, the FP4 expert
kernel, or detokenization. The corruption is overwhelmingly a dropped `<` — 38
of 49 malformed lines in the sampled run and 1977 of 1980 in the greedy run are
"missing opening delimiter" — which is a single-token defect, not a degradation
of model quality.

## Provider selection, and why it is not the obvious one

`--provider` needs a slug that supports every parameter in the request, or
OpenRouter returns `404 No endpoints found` once fallbacks are off:

- **`deepseek`** (first party) does not list `seed`. Returns 404.
- **`sail-research/fp4`** lists every parameter but returned HTTP 429 on every
  attempt, through five retries.
- **`relace/fp4`** also omits `seed` from `supported_parameters`, but accepts
  the request and serves it; the seed is presumably ignored. Chosen for the FP4
  arm on that basis.

The weights served by Relace and DeepInfra are not verified to be the official
checkpoint byte for byte. Neither provider publishes that. The comparison is
still decisive about the direction of the defect, because a 32 % to 0 % gap on a
dropped delimiter is not a weights difference.

# Run B (Hermes harness) scored against the Cachalot arm

Scored 2026-09-20 from `~/cachalot-corpus-pack/results` (38 Hermes session

## The harness did not cure the corruption, because the corruption never appeared

Every assistant turn in all 40 sessions was scanned, not only the final answer,
and the tool-call payloads with it: **zero malformed `#include` lines anywhere**,
including in the first draft of every task, before any tool had run. Nine of the
forty cases answered in one shot with no tool call at all, and those nine are
clean too.

So the harness had nothing to repair. What its tools actually caught, across
forty sessions, was two genuine defects: a `Buffer` indirection error in
`cpp-raii-edit` pass 2 and a traceback in `py-dataclass-validation` pass 1.
Everything else the tools did was verification of code that was already correct.

## Why the arm cannot answer the question that was asked

This run did not touch Cachalot. `~/.hermes/profiles/test-ds4-1/state.db` records
`{"model": "deepseek/deepseek-v4.1-flash", "provider": "openrouter"}` for all 41
sessions. It is the reference endpoint with a harness on top.

That means it cannot show that a harness makes the Cachalot runtime usable. It
was never given Cachalot output to fix. To answer that, run the same harness
against the local runtime.

## What it does show, with caveats

On the RUN.md decision table this lands on "reference clean, Cachalot corrupt",
which points at the runtime rather than at FP4 or at the model. The dropped `<`
is a token-level defect, and a 32 % to 0 % move is not something a system prompt
or a retry loop plausibly produces.

The caveats are real and should be stated wherever this number is used:

1. **Run A was never done.** RUN.md says to do the bare-API diagnostic first,
   precisely so a clean result cannot be attributed to the harness. This is B.
2. **The harness is in the context.** `system_prompt` is NULL in the database,
   but every first request carries about 22,480 prompt tokens, so roughly 22k
   tokens of tool schemas and scaffolding precede the task prompt.
3. **Reasoning was on**, effort medium. The Cachalot arm had none.
4. **Sampling was not matched.** Temperature, frequency penalty and the token cap
   are not recorded; Hermes defaults were used, not 0.6 / 0.2 / 2000.
5. **The provider was not pinned.** Hermes records only `provider: "openrouter"`,
   never the upstream stack per request. Forty requests may have landed on more
   than one quantization, which is the failure RUN.md warns about by name.
6. **seed1 / seed2 are two passes**, not pinned seeds.

Item 1 is the one worth fixing. `run_reference.py --provider <slug>` against the
same endpoint, no harness, matched sampling, is a few dollars and removes items
1 through 5 at once.
