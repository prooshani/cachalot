# Cachalot — Engineering Handoff, 2026-09-17

**State:** Cachalot 0.3.0 plus three commits, `main` clean, 51 tests passing.
**Machine:** Mac Studio M3 Ultra, 96 GiB unified memory, macOS 27.0.
**Read `docs/HANDOFF-2026-09-16.md` first.** It remains correct except where this document says otherwise.
Everything below was measured on this machine on 2026-09-17.

This session changed no numerics and produced no throughput change in the shipped configuration. What it
produced is knowledge: the two levers the previous handoff ranked first and second are both worth close to
nothing, and the reason decode is slow is not the one the project has been assuming.

---

## 1. The headline: decode is concurrency-starved, not bandwidth-starved

The previous handoff states that decode is bound by SSD bytes per token. That is half true, and the other half
changes what is worth doing next.

Measured with `benchmarks/decode_anatomy.py` at a 36 GiB budget, 512-token prompt, 64 decoded tokens:

| | ms per token | share |
|---|---|---|
| blocked inside the resident store | 140.1 | 51.5 % |
| attention, MoE kernels, head, Python | 132.1 | 48.5 % |
| total | 272 | |

60.7 misses per token, 990 MiB read per token, 6.06 ms per miss, **3.81 GB/s achieved**.

`benchmarks/expert_read_scaling.py` then reads random experts from the same bank through the real
`ExpertReader`, with no model loaded and nothing wired:

| concurrent loads | ms per expert | GB/s |
|---|---|---|
| 1 | 2.69 | 5.75 |
| 2 | 2.02 | 7.65 |
| 8 | 1.99 | 7.79 |
| 16 | 2.08 | 7.46 |

The drive and the reader deliver 7.8 GB/s at the `io_workers=8` the runtime already uses. Decode gets 3.81.
The difference is not latency, bytes, the destination or the page cache — all four were tested and excluded
(section 4). It is **concurrency**: a layer discovers about 1.5 misses, issues them, and waits. Roughly 1.5
reads are in flight at any moment, and 15.5 MiB in 6.06 ms at that concurrency is exactly 3.8 GB/s. Meanwhile
the drive is idle for the 48.5 % of each token that is compute, and the GPU is idle for the 51.5 % that is
reads.

Useful bytes are 60.7 x 15.48 MiB = 940 MiB per token, which is 121 ms at 7.8 GB/s, against 132 ms of compute.
**If reads and compute overlapped fully, a token would cost about 140 ms instead of 272: near 7 tok/s, without
reading one byte less or changing any numerics.** That is the prize, and nothing in the previous handoff's
ranked list targets it.

The obstacle is that overlap requires knowing a layer's misses before that layer runs, and the only mechanism
for that is routing prediction, whose precision collapses with lead time (section 3).

## 2. Engram on the internal SSD (old lever 7.1) is a null result

Committed as `287c1ca`.

The 3-bit Engram table inside the expert bank has identical row counts to the shipped FP8 table, layer for
layer (384,006,168 at layer 1 and 384,016,682 at layer 14), so row ids carry across unchanged. Its rows are
128 B in three regions against 264 B in two. On cold ids, 12,288 unique rows per layer, the shape of a
512-token prefill (`benchmarks/engram_rows_bench.py`):

| | per 512-token prefill |
|---|---|
| shipped FP8, USB drive | 1436 ms |
| affine 3-bit, internal SSD | 590 ms |

2.44x faster, and worth nothing. `benchmarks/engram_prefill_share.py` instruments a real prefill from outside
and shows the background prefetch already hides all of it:

    512-token prefill, 24.16 s: layer 1 read 629 ms starting 4 ms in, needed at 815 ms;
                                layer 14 read 1278 ms starting 6 ms in, needed at 8725 ms.
                                Blocked 0.0 ms, dequantization 10.2 ms.
    32-token prefill,  7.60 s:  blocked 0.0 ms, dequantization 1.5 ms.

Both layers' rows arrive before the layer that needs them, at both prompt sizes. Note also that the 3-bit row
costs three preads against two, so on a warm page cache it is *slower* (355 ms against 236 ms).

Moving Engram to the internal SSD is still worth doing one day as a robustness change, because it would retire
the dependency on the X10Pro. It is not a performance lever and it is not worth the Engram numerics risk.

## 3. Prediction knobs cannot buy the overlap (null result)

`CACHALOT_PREDICT_AHEAD` and `CACHALOT_PREDICT_TOPK` already exist, so this was pure A/B. All arms at 36 GiB,
512-token prompt, 64 decoded tokens.

Depth, one run each:

| arm | tok/s | MiB read/token | precision | wasted loads/token |
|---|---|---|---|---|
| ahead 1, topk 3 (default) | 3.67 | 990 | 76 % | 6.4 |
| ahead 2 | 3.79 | 1276 | 46 % | 25.7 |
| ahead 3 | 3.81 | 1633 | 31 % | 49.8 |

Depth raises drive utilization to 6.52 GB/s and spends nearly all of it on the wrong experts, because a router
two layers away is applied to an activation it never sees.

Width at depth 1, three interleaved pairs with a memory gate between runs:

| arm | tok/s | mean | expert wait ms/token | MiB read/token |
|---|---|---|---|---|
| topk 3 | 3.80 / 3.78 / 3.75 | 3.78 | 132-135 | 990 |
| topk 6 | 3.88 / 3.80 / 3.83 | 3.84 | 119-126 | 1357 |

+1.6 %, inside the 4 % noise band, for 37 % more bytes. Width does cut the blocking wait by about 9 ms per
token, and then gives it back elsewhere. Defaults are unchanged: `CACHALOT_PREDICT_AHEAD=1`,
`CACHALOT_PREDICT_TOPK=3`.

## 4. What is *not* the cause of the 6.06 ms miss

Each of these was measured and excluded, so do not re-test them:

- **The drive.** 7.8-8.7 GB/s at 8 concurrent loads on cold ids.
- **The destination.** Wired MLX slot buffers are faster than bytearrays, 1.60 ms against 1.79.
- **The GIL, or MLX running concurrently.** A background thread doing 4096x4096 bf16 matmuls costs the reader
  1.54 ms to 1.62 ms.
- **The page cache.** 1.77-1.83 ms per expert with it on, 1.78-1.94 with `F_NOCACHE`. In the runtime,
  `CACHALOT_PAGE_CACHE=1` is still worth having: 3.67 tok/s against 3.56 with it off.
- **The piece pool.** Nine scattered pieces per expert, eight of them submitted to a shared 16-thread pool,
  looked like an obvious convoy. It is not: the standalone reader runs the same code at 8 loaders and reaches
  7.8 GB/s.

## 5. Segmented LRU: opt-in, and budget-dependent

Committed as `6c5fb61`. `CACHALOT_EVICT=slru`, `CACHALOT_SLRU_PROTECTED` default 0.8. **LRU remains the
default.**

The offline replay (`benchmarks/simulate_policies.py`, now parameterized by expert size) reproduces
`docs/performance.md` section 3 exactly with FP4 bytes, so it is faithful. On the 3-bit bank at 44 GiB it
predicts decode hit rates of LRU 77.2 %, frequency+decay 77.9 %, segmented LRU 78.7 %. That settles the
contradiction recorded in section 7.2 of the previous handoff: the "39 % against 31 %" figure is not
reproducible and the "1 to 2 points" note is correct.

In the runtime, six interleaved pairs at 36 GiB, run in both orders:

    lru   3.56 3.60 3.61 3.59 3.61 3.50   mean 3.578 tok/s, 64.0 misses/token, 73.3 % hit
    slru  3.63 3.67 3.71 3.70 3.68 3.69   mean 3.680 tok/s, 63.8 misses/token, 73.4 % hit

Segmented LRU wins all six pairs, +2.9 %, while the hit rate barely moves — so the gain is not the one the
replay predicted, and its mechanism is not established.

At 44 GiB, the budget interactive chat actually uses, it reverses:

    lru   3.84 3.81 3.87 3.72   77.0 % hit, 55.2 misses/token
    slru       3.81 3.79 3.64   76.4 % hit, 56.5 misses/token

It costs 0.6 points of hit rate there, and a smaller protected share does not recover it (0.5 gives 76.3 % and
3.56 tok/s). Protecting twice-used experts helps while probation still holds most of the resident set and hurts
once the protected segment crowds out the churn LRU handles well.

## 6. Levers, re-ranked

1. **Read/compute overlap.** The only lever with a large ceiling (272 ms per token against about 140 ms if
   overlap were perfect). Knob-level speculation is exhausted; this needs a mechanism that knows a layer's
   experts earlier without a second approximation. Ideas not yet tested: predicting from the *post-attention*
   hidden state of the same layer rather than the previous layer's input, which trades lead time for accuracy;
   or a continuous background warmer that fills idle bandwidth with globally hot non-resident experts instead
   of per-layer guesses.
2. **Fewer bytes per expert** (old 7.5). Unchanged: a Q2-class bank would cut bytes and raise residency at
   once. Still blocked on GGUF k-quants that MLX cannot read.
3. **Startup hotlist preload** (old 7.4). Unchanged, helps the first prompt of a session.
4. **`F_RDAHEAD 0`** (old 7.6). Untested, cheap.
5. **Engram to internal SSD**, as robustness only (section 2).
6. **Eviction policy.** Closed. Section 5 is the final word: 1.5 points on paper, nothing or worse in the
   runtime at the production budget.

## 8. Operating note added this session

Benchmarks must not run back to back. macOS parks a finished run's memory on the inactive list, and
`guarded_run.sh`'s preflight counts it as reclaimable while a naive check does not; two arms started in
immediate succession produced a 1.32 tok/s outlier and two preflight refusals. Every A/B in this document ran
through a gate that waits for free plus inactive plus speculative pages to exceed the planned wired set, and
for pressure level 1, before starting the next arm.

The guardian also killed two runs, both correctly. In each case an unrelated `~/.hermes/node` process grew to
roughly 16-50 GiB while the benchmark held its wired set, swap grew past 2 GB and pressure reached level 2.
This is the same class of situation that panicked the machine on 2026-09-15. At a 44 GiB budget this machine
has no margin for another large process.

## 9. A wrapped copy-paste silently drops the expert bank

On 2026-09-17 three chat sessions decoded at 0.90, 1.05 and 1.30 tok/s where the same configuration had done
4.3-5.6 the day before. Nothing had regressed. The documented one-liner wrapped across five terminal lines, and
zsh executed them as five commands: a bare `VAR=value` on its own line sets a shell variable, which is never
exported to a child process, so only `PYTHONPATH` (which sat on the same line as the interpreter) reached the
runtime. `--temperature 0.6` landed on its own line and produced `zsh: command not found: --temperature`.

Without `CACHALOT_EXPERT_BANK` the runtime serves routed experts from `CACHALOT_MODEL_PATH`, and without that
too, `config.default_model_path()` discovers the FP4 checkpoint by scanning `/Volumes`. The sessions therefore
ran FP4 experts over USB at 1.0 GB/s, which is exactly what one tok/s looks like.

How to recognise it, from the session's own output:

- the `expert bank: … (affine, 3-bit, 14.77 MiB/expert, 15360 experts)` line is **absent**;
- `ready in … (expert budget B GiB, wired W GiB)` shows `W = B + 16.2`, the auto formula, rather than the
  `CACHALOT_MLX_WIRED_LIMIT_GIB` that was passed;
- in `/stats`, `resident_bytes / resident_experts` is 18,800,640 (FP4) instead of 15,482,880 (3-bit).

`scripts/chat.sh [budget_gib] [wired_gib]` now launches the qualified configuration and cannot be split by a
terminal. It also refuses to start beside a live runtime and checks that both paths exist.
